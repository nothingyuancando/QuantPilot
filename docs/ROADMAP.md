# QuantPilot 优化路线图

更新日期：2026-09-24。本文集中维护当前判断、交付顺序与验收标准；启动和学习入口见 [项目 README](../README.md)，历史批次记录保留在 Git 历史中。

QuantPilot 已具备较完整的 Agent 执行与治理基础。下一阶段围绕 **可信数据 → 可复现实验 → 持续研究 → 结果复盘** 提高研究价值，以真实交付质量、等待时间和复用率决定优化顺序。保留模块化单体，基础组件继续通过本地 Docker 管理。

本轮代码改进：

- **历史研究时间合同**：Query Rewrite v5 保存结构化起止日及带时区的截止时点，Run Plan 固化后由预取与 `quant_api_get` 共用。历史行情使用不复权日线的最后收盘作价格锚点，不再混入实时价格。盘中截止保守排除当日日线；日期无效、未来截止、参数冲突和不支持的接口明确拒绝。
- **计算与证据边界**：服务端在技术指标和回测计算前裁剪 `start/end`，缓存包含起点。财报读取不可变版本，校验截止时间、版本 ID、首次观测/公告可用时间；错误的 HTTP 200 响应也被拦截。缺失财报或公告保留为数据缺口。行情修订与历史证券池缺口继续标记为 partial。
- **首研与排队指标**：回查用户全历史首次提交，以完整 24 小时观察期计算完成率和首交付耗时，期间重试可贡献成功。回访、匿名、未成熟用户分别处理；截断或历史查询失败时指标明确不可用。Worker 首次排队增加中位数、P90 和异常时间计数。
- **Skills 合同维护**：query-rewrite 0.7.0、run-planner 1.1.0 同步 schema v5 和 failed 状态，保留可读取的存量 v4 相对时间合同，生成独立不可变版本包；补齐历史时间与模型未配置反例。

上轮的不可用预取响应拦截、原子缓存写入、过期读取并发修复和澄清状态拆分继续保留。本轮未增加数据库迁移或基础组件；有限行情维护只在本地执行，没有同步生产业务数据，也没有真实模型质量或性能提升百分比可报告。

## 交付顺序

下表是建议节奏，从下一轮启动计时，需按可投入人力和真实数据源情况调整。每一阶段达到验收条件后再扩大范围；工程减险、安全和可观测性随主线同步推进。

| 顺序 | 建议窗口 | 核心交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0 | 第 1–2 周 | 数据新鲜度、首次研究指标、失败定位、真实任务基线、关键用户路径回归 | 指标分母与证据可复核，至少 30 个分层真实研究任务完成首轮评估，建立延迟/成本基线 |
| P1-A | 第 2–6 周 | 结构化研究时点、PIT 参数贯通、数据版本与 lineage | 选定首批数据集通过未来数据泄漏反例；无法满足时点的查询明确拒绝或返回缺口 |
| P1-B | 第 6–10 周 | 版本化因子批处理、截面排名、行业中性化和因子评价 | 固定快照、固定版本可复跑，增量重跑幂等；评价只使用当时可得样本 |
| P1-C | 第 10–14 周 | 组合回测、样本外验证、实验登记与对照 | 费用、滑点、停牌、涨跌停、再平衡等约束有案例验证，同版本结果可重现 |
| P1-D | 第 14–18 周 | 研究假设、决策日志、定时跟踪、结果复盘 | 结论可回溯原始证据与实验，按预先设定的观察期记录结果和归因 |
| P2 | 随主线成熟推进 | 研究用模拟组合、风险分析、质量 canary 与生产 SLO | 风险计算与独立基准一致，模型/技能升级有对照和回退证据 |

**依赖关系**：数据时点与版本 → 因子快照 → 组合实验 → 研究复盘。真实质量评测、用户体验和结构治理贯穿各阶段。组合模型先服务研究和模拟，不接真实下单。

## P0：让质量和体验可以被判断

### 五个产品指标

| 指标 | 需要交付的定义与数据 | 验收 |
| --- | --- | --- |
| 首个有效研究完成率 | 明确首次有效提交、用户身份、观察窗口，以及重试是否属于同一次研究；用匹配 Mission 验收回执判定交付 | 跨窗口历史、匿名请求、失败重试、取消和等待澄清均有案例；不能用全部终态请求完成率替代 |
| 首次有效交付耗时 | 请求到首次有效交付，同时拆出排队、规划、预取、生成、验证/修复耗时 | 原始事件可重算，缺失/异常时间显式排除；同时报告样本量与 P50/P90/P95 |
| 证据首轮通过率 | 保存首次验证结果和最终验收结果 | 修复后通过不能回写成首轮通过；引用、快照与回执属于同一候选版本 |
| 成熟 7 日复用率 | 以首个研究日期建立 cohort，只统计已完整经历观察期的用户 | 未成熟用户不进入分母；窗口内重复研究率继续单独展示 |
| 单任务成本 | 关联规划、执行、修复及工具调用的 usage、价格版本与币种 | 账单缺失显示未知；重试与共享开销有归因，不能直接把 token 数当金额 |

连续两周收集有效样本后设定首批改善目标；优化同时报告样本量、数据源、模型/技能版本和工作树版本。没有样本时展示“暂无”，不填写推测的改善百分比。

### 真实体验与失败定位

先恢复模型可用性并核查市场服务 readiness；对日历和研究所需证券池列出补数范围、dry-run 数量与上限，再单独执行有限补数。代码发布与数据操作分别记录，不能把旧行情当成当前市场。

建立至少 30 个任务的分层样本，覆盖个股、ETF、比较、选股、财报和回测，并包含澄清、过期行情、上游失败、取消、Worker 重启和修复。保存输入、阶段时间、证据、验证结果及用户能看到的恢复动作；测试工作空间与业务数据隔离。

先解决发生最多或阻断交付的问题。页面持续显示已知阶段和可执行动作；失败后保留输入与证据，刷新能恢复状态。桌面与移动端均验证等待、失败、重试和权限拒绝，不只验收成功截图。

对应入口：[研究闭环指标](ops-platform-guide.md)、[Agent 评测](evals-guide.md)、[第一次研究教程](learning/first-research.md)。

## P1-A：可信数据底座

先选定日线与财报两类数据贯穿全链路，完成后扩大覆盖，避免把所有接口“加一个日期参数”视为 PIT 完成。

1. 已实现首批结构化时间合同与读取约束；下一步补齐行情首次观测/修订、复权事件和历史证券池快照，再扩大支持接口。不要把日期裁剪等同于完整 PIT。
2. 区分交易/报告日期、公告时间、首次观测时间和修订版本。财报只使用截止时点已公告且已观测的不可变版本；真实历史回填需要可验证出处。
3. 把复权事件、退市证券、历史行业/指数成分纳入版本管理，分别验证未来信息泄漏和幸存者偏差。
4. 每个数据集记录 provider、时间范围、schema、内容 hash、许可/用途限制、freshness、coverage、异常和跨源差异；证据能追溯到具体原件。
5. 自动采集任务提供幂等键、检查点、限额和有限重试；补数进程崩溃后的恢复不能继续依赖内存任务。

验收采用固定历史时点与后续修订的成对样本：新增未来公告或新修订后，原时点实验的数据 hash 和结果必须保持不变；不支持的历史数据明确不可用。只有覆盖完成并通过反例的数据集可以标注 PIT。

对应入口：[数据生命周期](data-lifecycle.md)、[数据字典](data-dictionary.md)、[市场数据源知识](market-data-source-knowledge.md)。

## P1-B / P1-C：因子平台与可复现实验

日频因子先覆盖 MA、动量、波动、回撤、成交额放大和基本面质量。采用可重入批处理，记录因子定义版本、数据版本、计算参数与样本池；支持截面排名、行业中性化、IC/IR、换手、相关性和漂移分析。行业映射必须匹配研究日期。

实验登记保存数据快照、证券池、策略代码/版本、参数、执行环境、随机种子和结果 hash。单标的回测作为回归基准保留，组合回测增加基准、目标权重、再平衡、费用、滑点、停牌/涨跌停、容量与现金处理，再加入样本外和 walk-forward。

验收要求：

- 相同快照与版本重复执行结果一致；改动费用或再平衡参数后，差异可归因。
- 因子批处理重复执行不产生重复记录，失败后能从检查点继续。
- 使用独立小型手算案例验证收益、仓位、现金与费用；不以模型自己给自己的解释作为正确性证据。
- 未实现的交易约束显示为限制，不能宣传为真实可执行收益。

对应入口：[策略平台](strategy-platform-guide.md)、[生成工作空间契约](generated-workspace-contract.md)。

## P1-D / P2：持续研究和结果复盘

把观察池、报告与 webhook 扩展为“假设 → 证据 → 实验 → 决策记录 → 定时跟踪 → 结果”的持久对象关系。报告写明研究时点、有效期、触发条件和不确定性；后续结果追加记录，不覆盖原判断。通知发送遵守现有授权和去重约束。

在此基础上建立研究用 Portfolio/Holding/Snapshot，计算行业暴露、集中度、回撤、情景压力和收益归因。模拟成交模型、基准和数据缺口可见，信号命中率按预先约定的窗口计算。

验收从一条完整研究链开始：打开原结论能找到数据和实验，观察期到达后能解释结果变化；重复运行定时任务不会重复报告、快照或推送。

对应入口：[投研自动化](research-automation-guide.md)。

## 贯穿全程：Agent、Skills 与质量运营

先提高已有核心技能的可信度，保持内置可信市场的边界。在线编辑、发布、版本固定与回退已有基础，无需重新建设平行安装体系。

| 优化方向 | 下一步交付 | 验收 |
| --- | --- | --- |
| 运行兼容性 | 明确 Agent runtime/phase、typed tools、模型能力、技能版本的兼容矩阵 | 安装前展示缺少的能力；执行前再次检查，不能仅凭安装成功声明可运行 |
| 维护与回退 | 对 revision 冲突、不可变快照、项目固定、原子生效与回退做故障回归 | 编辑冲突保留草稿；失败发布不改变当前版本；跨进程重启后固定版本和回退结果一致 |
| 版本与任务证据 | 记录每次任务实际加载的 skill/capsule/tool/model 版本与内容 hash | 旧实验能定位完整配置；工作区参考镜像不能绕过平台版本选择 |
| 金融对抗评测 | 扩充标的歧义、幻觉引用、未来函数、复权错误、过期行情、财报修订、过度投资建议等案例 | 按能力报告失败分类与严重度；关键金融错误阻止晋级 |
| 生产回放与 canary | 脱敏回放、隐藏集、候选/基线对照，观察质量、成本和延迟 | 回放不重复外部副作用；候选退化时保留旧版本并可回退，不能只看平均分 |

真实模型评测与确定性合同评测分别出具证据。评测数据不能进入被评模型的提示或知识检索；新增 Provider 需证明解决现有瓶颈。

对应入口：[Skills 治理](skills-governance.md)、[Skills 编写教程](learning/07-skills-authoring.md)、[评测指南](evals-guide.md)。

## 贯穿全程：结构、性能、安全与生产

模块门禁的 9 处目标线告警集中在聊天页/消息、运行引擎、脚手架模板、策略页和 Skills 页面。已拆出的 validation、prefetch、Python contracts、Worker preparation 和 Skills 服务继续维持边界，旧门面不恢复。

| 方向 | 优先动作 | 验收证据 |
| --- | --- | --- |
| 结构瘦身 | 依次拆聊天提交/状态、ChatLog 消息渲染、run-engine 编排、Skills 编辑状态；提取模板重复逻辑 | 职责单一、调用方直接使用公共能力；删除旧实现，降低对应预算；模板变更需实际 Next build |
| 入口与依赖 | 根据使用率和导入图合并重复入口，审查零业务调用的依赖、包装层和脚本 | 删除前确认动态加载、运行与构建引用；发布检查和关键用户路径不退化 |
| 性能 | 基于阶段 trace 处理重复 IO、批量查询、跨项目并发上限、同键请求合并、缓存命中率与大列表渲染 | 同任务集和负载比较吞吐、P95、内存、上游请求数；结果一致；合成耗时不充当真实交付时间 |
| 可观测性 | 串联 request/job/Mission/experiment ID，增加阶段耗时、错误率和模型成本；建立 SLO、告警与排障链接 | 用户失败可定位到阶段和数据源；受控演练可触发并解除告警 |
| 安全与恢复 | 保持权限/配额/沙箱/审批/fencing；补 SBOM、镜像扫描、恢复演练和持久 Memory 治理验证 | 负向权限测试、依赖审计与恢复记录可审查；凭据和业务数据不进入代码库 |
| 测试与发布 | 补高风险 API 行为覆盖，再逐步提高关键域覆盖率门槛；检查绑定版本 | release gates、隔离数据库测试、UI smoke 和模型证据分别记录；部署后核对实际运行 SHA |
| Docker 组件 | TimescaleDB 保存权威数据；Redis、ClickHouse、Loki/Grafana/Alloy 按职责运行 | readiness、资源预算、数据卷与恢复步骤明确；不新建重复存储服务 |

仅在团队协作成为实际需求时加入 Organization、OIDC、共享研究、审核和成本中心。继续避免重复桌面壳、新控制台堆叠、过早微服务化，以及用成交额代理冒充真实资金流。

对应入口：[项目结构](project-structure.md)、[模块边界](module-boundaries.md)、[基础设施](infrastructure.md)、[发布手册](release-runbook.md)。

## 下一批交付

1. **历史数据版本闭环**：在已贯通的时间合同上补行情修订、复权事件与历史成分；固定时点的原实验不被后续修订改变，实验记录注明数据许可和覆盖缺口。
2. **阶段耗时与成熟复用**：复用已有事件记录规划、预取、生成、验证/修复首轮与重试耗时，建设成熟 7 日复用；费用按 usage 与价格版本归因，无法计价时显示未知。
3. **真实任务基线**：恢复模型和市场 freshness 后运行至少 30 个分层任务，区分合成合同、真实模型和供应商证据；按结果推进因子批处理、组合实验和关键页面性能。

## 每批交付要求
